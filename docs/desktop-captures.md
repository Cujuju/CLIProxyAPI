# Desktop capture spool v1

Authenticated v8 management operational API, independent of request-log files and usage accounting. Capture is disabled by default. It never resolves short log IDs or treats upstream execution UUIDs as inbound IDs.

`PUT /v8/management/observability/captures/lease` takes `{ "enabled": true }` and returns `{ "leaseSeconds": 60, "bodyLimit": 262144 }`. True renews a 60-second lease; false disables capture, invalidates active generations, and clears the memory spool. Lease is ephemeral operational state, not a persisted proxy setting. The desktop application stores explicit policy in its encrypted database. No config PUT is needed.

`GET /v8/management/observability/captures?after=<uint64>` returns `{ "version": 1, "epoch": "<process UUID>", "dropped": 0, "records": [] }`. At most four records are returned. Each record has stable `id` (capture UUID), full `traceId` (inbound logging request UUID), epoch, monotonically ordered finalization sequence, startedAt, method, path without query, downstream HTTP status, state, reason, request/response text and their content type/encoding. Headers are excluded. The desktop SSE `trace_id` matches `traceId`; SSE request_id describes an upstream attempt and must not be used for capture lookup.

Clients persist records and cursor atomically, then use the final sequence as `after`. Repeated reads are replayable. Compare epoch on every read; when it changes, discard the old cursor and fetch after=0. Sequence gaps, `dropped` and epoch changes report incompleteness. The counter includes active-limit rejection, queue overflow, ring eviction and generation/lease rejection. Tail drops need not yet create a visible sequence gap. Restart destroys memory and resets counters; loss before the client's first observed epoch is unknowable.

The inference path only copies bounded heads and tails of consumed/written HTTP bytes or already-decoded downstream WebSocket application messages. It never reads ahead, decompresses capture data, or writes capture files/SQLite. Separate permit pools allow 16 HTTP and 16 WebSocket captures so long-lived Codex sockets cannot starve HTTP. An eight-record nonblocking revision/finalization queue and a 64 MiB/256-record spool bound retained memory (the spool budget counts body and frame payloads, excluding object/metadata overhead). The worker normalizes/decompresses data. There is no guaranteed delivery: proxy crashes, overflow, lease expiry or disconnected clients may lose captures. New inbound requests while the lease is off are not captured retroactively.

HTTP retains at most 8 MiB wire bytes and 8 MiB decoded bytes per direction. Identity, gzip/x-gzip, zstd, and up to two stacked encodings are decoded in reverse order in the spool worker. Zstd uses one decoder goroutine with an 8 MiB memory/window limit. Expansion, wire truncation, incomplete compressed streams, unsupported encoding, invalid UTF-8, incomplete request consumption, downstream write error and cancellation are explicit partial states. Unsupported/undecodable encodings retain bounded base64 wire text, with requestDecoded/responseDecoded false. Original encoding labels remain on decoded bodies.

For the supported Codex `/v1/responses` and `/backend-api/codex/responses` WebSocket handlers, SDK hooks capture actual received application messages and successfully written responses (including protocol errors and interrupt messages). Existing permessage-deflate processing yields readable payloads before the hook. Capture limits are 128 messages per connection, 8 MiB per message, and 8 MiB per direction; earliest and newest messages survive overflow; omitted middle messages leave index gaps. `format:websocket` records contain structured `frames` with index/direction/time/type/payload/truncated plus readable request/response transcripts. Socket-path hooks only copy bounded heads and tails and offer nonblocking updates. Normalization/UTF-8 conversion runs in the spool worker. Revision records share captureId/full trace but have successive sequences, allowing encrypted desktop persistence and inspection before socket closure. Open snapshots are pending; bound violations/write failures/disconnects are partial; a clean finalized message set is complete. Latest revisions replace earlier archive content. WS control ping/pong/close frames, other WebSocket protocols, provider-hidden data, and upstream executor bodies are outside the boundary.

`complete` covers only observed downstream bytes/messages within these bounds; it proves neither upstream success nor semantic completeness. Unauthenticated requests contain no payload. Rejected upgrades without an upstream execution do not create usage records; independent metadata is visible only when capture is opted in. Deliberately discarded generations after opt-out do not increment the proxy drop counter. Proxy drops and observed client sequence gaps overlap and must not be added together.

The app encrypts durable archive data and FTS, applies body retention and byte budgets there, and retains stable identities independently of Activity row IDs. Existing plaintext request logging, if separately enabled, keeps its existing semantics; the lease does not control it.

HTTP `requestCut`/`responseCut` are always present and null for a complete side; clients treat their absence as a proxy before per-side cuts (first 256 KiB only). Frame `cut` is absent for complete frames. Each cut has `offset` (UTF-8 byte position between emitted head and tail) and `omitted` (body bytes omitted, or null when unknown). Cut points preserve whole UTF-8 characters. Encoded wire overflow decodes only the retained prefix and reports unknown omitted bytes at the emitted end. Per-side capture memory is bounded by 8 MiB (head plus tail), so a request adds at most its size up to that bound.
